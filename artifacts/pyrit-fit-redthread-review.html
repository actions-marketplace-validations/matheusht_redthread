What “fit” means here

PyRIT fits if it reduces target-connection work without changing RedThread’s core loop:

attack → judge → defend → replay → promotion evidence

RedThread’s source-of-truth docs say PyRIT is already used as foundational plumbing, not as a fork or replacement for RedThread algorithms. The product boundary is closed-loop evidence: attacks, JudgeAgent scoring, defense synthesis, replay, and promotion state.

Keep / add

  • Keep RedThreadTarget as the sole provider send boundary.
  • Keep PyRIT PromptTarget.send_prompt_async under that wrapper.
  • Add only if needed hidden target-capability validation before multi-turn, system-prompt, multimodal, or HTTP target paths.
  • Mine converter ideas for internal attack variation, but expose them through RedThread strategy presets, not PyRIT flags.
  • Keep controlled live adapter metadata and canary containment around sends.

Do not add

  • No wholesale migration to PyRIT attack executors/orchestrators.
  • No PyRIT scorer as confirmed-finding authority.
  • No PyRIT memory as canonical campaign, replay, or promotion memory.
  • No PyRIT scanner/GUI wrapper mode in RedThread right now.
  • No version upgrade just to match docs; upgrade only for a named capability and migration test.

Why this is the simplest useful shape

Naval’s “simplest” note argues that complex systems scale when you remove unnecessary parts and question requirements before optimizing. Applied here: the requirement is not “use more PyRIT.” The requirement is “run trustworthy RedThread campaigns against more targets with less duplicated provider code.”

That means the adapter is additive when it hides complexity. It becomes non-additive when it creates a second orchestration, scoring, memory, or operator semantics layer.

Recommended next step

  1. Freeze the architecture rule: PyRIT is provider plumbing only.
  2. Add a small adapter contract test suite if missing: target send, metadata record, canary block, controlled live deny, provider error record.
  3. Write one optional capability-check spike behind the current factory layer. Acceptance: no new CLI flags, no new evidence states, no migration to PyRIT orchestrators.
  4. Defer PyRIT upgrade until a concrete blocker appears. If upgrading, test against the v0.13 breaking changes first.
