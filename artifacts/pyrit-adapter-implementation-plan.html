Keep PyRIT thin. Harden the adapter seam.

Plan for making PyRIT more useful to RedThread without letting it become RedThread's orchestration, judge, memory, or product surface.

RecommendedBounded adapter-hardening tranche.
Main riskPyRIT version drift: RedThread pins pyrit==0.12.0; public docs and main branch are already ahead.
Success barMore target reach and better send truth with no new user-facing complexity.

1. Decision

Build only the adapter-hardening layer. Do not adopt PyRIT attacks, orchestrators, scorers, memory, GUI, or broad modes. This follows the simplest useful path: improve the boundary RedThread already owns.
QuestionAnswer
What will it impact?The target/send seam: RedThreadTarget, factories, runtime target construction, shared send helpers, execution metadata, canary containment, and controlled live adapter paths.
What will it leverage?PyRIT prompt targets, OpenAI-compatible endpoints, rate-limit/retry behavior, target capability metadata, converter modality contracts, and message/memory mechanics.
Improve in what sense?Target reach, capability honesty, provider-send reliability, execution evidence quality, and reduced local adapter drag.
What must not change?LangGraph supervisor, PAIR/TAP/Crescendo/MCTS logic, JudgeAgent authority, defense synthesis, replay promotion, and RedThread memory truth.

2. Current RedThread state

  • pyproject.toml pins pyrit==0.12.0.
  • src/redthread/pyrit_adapters/ is small: 659 LOC across adapter files.
  • RedThreadTarget.send() wraps PyRIT send_prompt_async(), builds a single user message, records execution metadata, and applies canary containment.
  • send_with_execution_metadata() is already the shared safe-send helper used by judge, tools, telemetry, replay, and canary tests.
  • Existing docs already say PyRIT is infrastructure plumbing, not a fork or product replacement.

The new piece is RedThreadTargetCapabilities: a RedThread-owned dataclass or Pydantic model that copies only the stable capability facts RedThread needs. It shields the rest of the codebase from PyRIT 0.12 vs 0.13 API churn.

5. Implementation plan

Slice 1
Capability contract
Add src/redthread/pyrit_adapters/capabilities.py with RedThreadTargetCapabilities, TargetRequirement, and helper functions that read PyRIT 0.12 target.capabilities. Keep the file under 200 LOC.
Slice 2
Factory wiring
Extend _build_pyrit_target() / factories to attach or expose normalized capabilities. Do not add new settings unless required. Default behavior remains unchanged for current text-only sends.
Slice 3
Gate before send
Add explicit preflight checks at the adapter boundary for modes RedThread actually uses: multi-turn, JSON output, multi-message pieces, modalities, and editable history. Unsupported modes fail before provider calls.
Slice 4
Evidence metadata
Record capability decisions in execution metadata when relevant: required capability, result, target model, and whether failure happened before send. This improves operator truth without changing promotion semantics.
Slice 5
Version guard
Add tests that assert the pinned PyRIT 0.12 capability API exists. Add a migration note for 0.13 TargetConfiguration. Do not upgrade PyRIT in this tranche.
Slice 6
Optional converters later
After capability gates pass, consider a separate tiny allowlist for text-only converter adapters behind attack strategy internals. This is not part of the first implementation unless you approve it.
