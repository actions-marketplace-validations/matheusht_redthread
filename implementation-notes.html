Questions answered during implementation

  • Does any current JudgeAgent path request PyRIT JSON mode? No. src/redthread/evaluation/judge.py sends plain text prompts through send_with_execution_metadata(); it parses text after the response. No current JudgeAgent call sets PyRIT JSON response metadata.
  • Do current multi-turn algorithms rely on target-side memory? No. Crescendo explicitly documents client-side history and compiles full history into each target prompt. MCTS reconstructs history from MCTSTree and compiles it into prompt text. PAIR/TAP also pass prior context as prompt text, not target memory state.
  • Can execution metadata carry capability preflight details without changing ExecutionRecord? Yes. ExecutionMetadata.metadata is copied into ExecutionRecord.metadata, so the implementation adds capability_preflight there and leaves ExecutionRecord unchanged.

Design decisions

  • Used CapabilityRequirement as an optional argument with default text-only behavior. Existing sends require no changes.
  • Mapped PyRIT 0.12 TargetCapabilities into RedThreadTargetCapabilities to shield RedThread from PyRIT 0.13 drift.
  • Defaulted targets without a capabilities attribute to text-only. This is safest for test doubles and unknown adapters.
  • Added optional capability forwarding to shared send helpers, but only sends the keyword when explicitly provided. Existing legacy fallback behavior stays unchanged for normal calls.
  • For OpenAI targets, underlying_model=model is now passed so PyRIT can apply known model capability profiles, such as GPT-4o image input support.
  • For Ollama and llama.cpp OpenAI-compatible targets, custom capabilities are now text-chat only: multi-turn and multi-message pieces are true, JSON output is false. This avoids claiming JSON support for local OpenAI-compatible servers by default.
  • Unsupported preflight failures include failure_stage=capability_preflight, provider_call=false, requirement metadata, and target capability snapshot.
  • Phase 6 stayed as planning only. The converter allowlist plan rejects broad PyRIT converter adoption and allows only future deterministic text-in/text-out adapters if replay evidence proves need.

Deviations

  • No material spec deviations. One interpretation: the preflight gate runs after existing canary/live interception and before PyRIT message construction. This matches the planned safety order and avoids weakening containment.
  • Phase 3 did not add settings or CLI flags. The best RedThread fit was to adjust hidden factory/runtime construction only.
  • Phase 6 did not add converter code. The phase plan said post-gate converter planning only, so implementation means durable planning documentation, not runtime behavior.

Tradeoffs

  • Chose adapter-only gates instead of touching algorithms. This avoids false capability requirements for flows that already flatten history client-side.
  • Did not add report summary output. Logs-only matches the approved answer and avoids operator noise.
  • Chose conservative local-backend capabilities over PyRIT's OpenAIChatTarget default JSON claim. If a local server later proves JSON-mode support, add an explicit capability override in a future slice.
  • Rejected broad converter support because it adds feature volume before proof. Future converter work should start with a tiny deterministic text-only allowlist, no CLI flags.
